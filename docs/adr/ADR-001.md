# ADR-001: Capas simples para persistencia; el seam de notificación ya cubre el próximo cambio conocido

## Estado

Aceptado — 2026-11-13

## Contexto

Tras integrar Chain of Responsibility, Strategy y Observer sobre el sistema de solicitudes de reembolso, corresponde decidir si el proyecto debe migrar a arquitectura Hexagonal completa (puertos e interfaces intermedias para persistencia y notificación) o mantenerse en capas simples.

La Guía (sección 6.2) sitúa la arquitectura Hexagonal en sistemas que sobrevivirán 3 años o más con cambios de infraestructura. Se evalúa ese criterio por separado para cada dependencia externa, con los datos del proyecto:

- **Persistencia.** Hay un solo motor (H2 en memoria durante el desarrollo, con Spring Data JPA) y no existe ningún plan de cambiarlo. `RepositorioSolicitudesJpa` extiende `JpaRepository` directamente y `SolicitudReembolso` lleva `@Entity`, de modo que no hay capa de mapeo ni interfaz intermedia.
- **Notificación.** Contabilidad anunció que el próximo trimestre integrará una API externa para pagar las solicitudes aprobadas. Es el único cambio de infraestructura con fecha conocida. El servicio ya depende de una abstracción (`ObservadorCambioEstado`, inyectada como `List<ObservadorCambioEstado>`), no de los notificadores concretos.

## Decisión

1. **Persistencia: capas simples.** `SolicitudReembolsoService` sigue dependiendo directamente de `RepositorioSolicitudesJpa`, sin interfaz de puerto. Un puerto hoy sería una abstracción especulativa (YAGNI) sin ningún caso de uso que lo requiera.
2. **Notificación: sin cambios.** `ObservadorCambioEstado` ya es el punto de extensión necesario. `NotificadorContabilidad` puede reemplazar su implementación interna por una llamada a la API externa sin modificar `SolicitudReembolsoService` ni los demás observadores.

## Consecuencias

Positivas:

- No se agregan interfaces ni mappers de persistencia sin un caso de uso real que los justifique.
- El único cambio de infraestructura con fecha conocida (la integración de Contabilidad) ya tiene su punto de extensión listo.
- Los límites que sí existen entre paquetes se verifican con ArchUnit, de modo que la decisión no depende de la disciplina del equipo.

Negativas:

- Si en el futuro se necesita cambiar de motor de base de datos o tener un segundo consumidor del repositorio, el puerto de persistencia deberá introducirse retroactivamente. Se acepta esa deuda técnica de forma consciente.
- El dominio está acoplado a JPA mediante `@Entity`: un cambio de tecnología de persistencia tocaría la clase `SolicitudReembolso`.
- Un revisor que espere simetría total (puertos en todas las dependencias externas) puede interpretar la asimetría como inconsistencia si no lee este ADR.
- **El seam cubre la estructura del código, no la fiabilidad.** `SolicitudReembolsoService` recorre los observadores de forma síncrona y sin aislar fallos. Una llamada lenta a la API de Contabilidad bloquearía la petición que cambia el estado, y una excepción interrumpiría a los observadores siguientes (incluida auditoría) cuando el nuevo estado ya está guardado, además de devolver un error al cliente. Esto no se resuelve ahora (no hay todavía integración que lo exija); se decidirá, junto con reintentos o una cola, cuando se implemente la API de Contabilidad.

## Cuándo reconsiderar

- Aparece un segundo motor de base de datos, o un segundo consumidor del repositorio: introducir el puerto `RepositorioSolicitudes`.
- La integración con Contabilidad requiere reintentos, entrega garantizada o no bloquear la petición: revisar cómo se invoca a los observadores.
